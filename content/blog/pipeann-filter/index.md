## 前言

过滤向量检索（Filtered ANN）在内存场景下已经有不少工作，但在 SSD 场景中会更麻烦：一次图遍历不仅涉及距离计算，还可能触发随机 I/O；如果过滤条件处理得不好，系统要么读太多无效节点，要么过早剪枝导致图搜索质量下降。

PipeANN-Filter 关注的是 **SSD 上的带过滤 ANN 搜索**。它试图在 PipeANN 这类磁盘图索引的基础上，引入 label filter 和 range filter，并根据查询选择 pre-filtering、in-filtering 或 post-filtering 等不同策略。

本文整理自论文分享录音稿，重点记录其系统结构、推测性过滤思想、混合策略选择，以及一些实验和讨论中的疑点。

## 背景：SSD ANN 与过滤搜索

### SSD ANN 的基本结构

SSD 上的 ANN 索引通常会把索引拆成两部分：

1. **DRAM 部分**：存储较小、访问频繁的信息，例如量化后的向量、入口点、缓存结构或部分导航信息；
2. **SSD 部分**：存储完整向量、邻接边、记录数据以及其他较大的索引信息。

DiskANN、SPANN、Starling、BANG 等工作大多都遵循类似思路：尽可能让内存保存压缩后的全局信息，把大体量的向量和邻居列表放到 SSD 上。

搜索阶段也常常被拆成两步：

- 先扩展候选集，尽量找到可能接近查询点的一批节点；
- 再读取完整向量或更多信息做精排。

一些 SSD ANN 系统为了减少 I/O，会在候选扩展阶段尽量避免读取完整向量，只使用内存中的量化表示或重排后的块结构来筛选候选。

### 过滤条件带来的额外挑战

在带过滤条件的 ANN 中，候选向量不仅要距离近，还要满足 label 或 range 条件。内存场景下，一个常见做法是严格判断：

- 向量满足过滤条件，则参与搜索或进入结果集；
- 向量不满足过滤条件，则直接跳过。

但在 SSD 图索引中，严格过滤会带来两个问题。

第一，**图连通性可能被破坏**。如果搜索过程中只能经过满足过滤条件的节点，那么低选择性过滤下可走的边会非常少，搜索容易中断或陷入局部区域。

第二，**属性判断本身可能带来 I/O**。如果标签或数值属性不在内存里，每次判断一个节点是否满足过滤条件都可能需要访问 SSD，这会显著增加延迟。

因此，PipeANN-Filter 的核心问题可以概括为：在 SSD 过滤搜索中，如何用较少的内存和 I/O，尽量保留图搜索连通性，同时避免访问太多无效候选。

## 核心思想：推测性过滤

PipeANN-Filter 最关键的设计是 **推测性过滤**（speculative filtering）。它不要求过滤判断必须完全精确，而是使用一个近似成员判断函数：

> `is_member_approximate(x, filter)`

这个函数满足 **no false negatives**：

- 如果函数返回 `false`，那么向量一定不满足过滤条件，可以安全跳过；
- 如果函数返回 `true`，那么向量只是“可能满足”过滤条件，后续还需要精确验证。

也就是说，它允许假阳性，但不允许假阴性。

这种设计的意义在于：

- 假阳性节点可以作为图遍历中的“桥接节点”，帮助搜索穿过原本会被严格过滤切断的区域；
- 最终结果仍然会做精确过滤，因此不会把不满足条件的向量返回给用户；
- 代价是候选集中会混入一些无效节点，可能增加距离计算和 SSD 读取。

它和严格过滤的区别在于：严格过滤会在搜索过程中尽量排除所有不合格节点，而推测性过滤把一部分“可能合格”的节点保留下来，让它们参与图遍历，最后再过滤。

## 系统架构

PipeANN-Filter 的索引大体分为两类：向量索引和属性索引。

### 向量索引

向量索引用于支持基础 ANN 搜索。根据录音稿中的描述，论文中的 PipeANN-Filter 与原始 PipeANN 略有差异：它的边信息和索引信息主要从 SSD 访问，DRAM 中主要保留量化后的向量权重或轻量信息。

对于 in-filtering，系统还会用到 **二跳邻居**。直觉上，二跳邻居可以在过滤图被稀疏化后提供更多可探索路径，缓解低选择性下的一跳邻居不足问题。

在访问某个点时，系统不仅检查一跳邻居，也可能检查二跳邻居是否近似满足过滤条件，然后把符合近似条件的节点加入候选扩展过程。

### 属性索引

属性索引用来判断节点是否满足过滤条件，分为 label filter 和 range filter 两部分。

#### Label filter

对于标签过滤，PipeANN-Filter 使用两类结构：

- **DRAM 中的 Bloom Filter**：用于快速判断某个节点是否可能属于某个标签；
- **SSD 上的倒排索引**：保存标签到向量 ID 集合的映射，可用于精确或更小集合的读取。

此外，系统还会维护 label count 等统计信息，用于后续的 cost estimation，也就是查询到来时估计应该使用哪种过滤策略。

论文区分了稀有标签和高频标签：

- 对于稀有标签，直接从 SSD 的属性索引中读取对应倒排列表。因为集合本身较小，读取和判断成本可控；
- 对于高频标签，直接读取倒排列表可能太大，因此使用 Bloom Filter 在内存中做近似判断。

这样设计的关键权衡是：稀有标签追求更精确的候选集合，高频标签则优先避免大量 SSD 读取。

#### Range filter

对于范围过滤，PipeANN-Filter 的处理比较粗粒度。它把数值属性压缩到 1 Byte，也就是映射到 256 个桶中，形成一个直方图式的表示。

判断一个向量是否近似满足范围条件时，只需要看该向量所在桶与查询范围是否有交集：

- 如果桶与范围没有交集，则一定不满足；
- 如果桶与范围有交集，则可能满足。

这同样符合 no false negatives 的要求，但会引入假阳性。桶越粗，误判越多；桶越细，内存和索引开销越高。

这个 range filter 的优点是实现统一、存储很小；缺点也很明显：256 桶的粒度可能过粗，尤其在数值分布不均或查询范围很窄时，假阳性比例可能很高。

## 三种过滤策略

PipeANN-Filter 并不是固定使用一种过滤方式，而是根据查询和过滤条件估计成本，在 pre-filtering、in-filtering 和 post-filtering 之间做选择。

### Pre-filtering

Pre-filtering 是先根据过滤条件取出候选集合，再在该集合中做 ANN 搜索或距离计算。

对于 label filter，pre-filtering 可以直接读取 SSD 上的倒排列表。

如果查询是 AND 谓词，系统还会做一个优化：优先读取选择性更低的标签集合，暂时忽略高选择率标签。因为 AND 条件下最终结果一定属于所有标签的交集，低选择率标签已经能把候选集合缩得很小，后续再对小集合补充检查高频标签即可。

这个策略适合选择性很低、过滤后候选集合很小的场景。

### In-filtering

In-filtering 是在图遍历过程中做过滤判断。

严格 in-filtering 会只扩展满足过滤条件的节点，而 PipeANN-Filter 使用推测性过滤：只要节点“可能满足”条件，就允许它参与图搜索。

它的好处是保留一部分桥接节点，提升图遍历连通性；坏处是候选池中会混入假阳性节点，增加 SSD 读取和距离计算。

录音稿里提到，这部分和一些实践中的“先让更多节点进入候选，再在最终结果阶段做精确过滤”的思路很像。不同之处在于，PipeANN-Filter 不是把所有节点都当成可能有效，而是用 Bloom Filter 或属性桶先做一层近似过滤。

### Post-filtering

Post-filtering 是先按普通 ANN 搜索得到一批近邻候选，再对结果做过滤。

它适合过滤选择性较高的场景：如果大多数近邻本来就满足条件，先搜索再过滤的额外代价较低。

但如果选择性很低，post-filtering 可能需要搜索非常多候选才能得到足够的有效结果，因此会退化。

## Cost Model：如何选择策略

PipeANN-Filter 使用一个 cost model 来判断每个查询应该采用 pre、in 还是 post。

这个模型大致考虑两类放缩。

第一类是 **选择性放缩**。如果过滤选择率为 $s$，为了找到 $L$ 个有效节点，可能需要探索约 $L / s$ 个候选。

第二类是 **精度放缩**。由于推测性过滤会带来假阳性，如果近似判断的精度为 $p$，那么为了获得等价于原来 $L$ 个有效候选的搜索质量，可能需要扩大候选池到约 $L / p$。

模型还会把 I/O 和距离计算赋予不同权重。录音稿中提到，论文根据本地测量认为一次 I/O 的开销大约相当于 10 次距离计算，因此在总成本中给 I/O 更高权重。

这个 cost model 的目标是让系统在查询前快速估计三种策略的开销，然后选择代价最低的方案。

不过，这里也存在一个讨论点：这种模型高度依赖对选择性、假阳性率和数据分布的估计。如果 label 与向量空间的分布强相关，或者标签在空间中高度聚集，简单的 $L / s$ 估计可能并不准确。

## 实验与结果解读

### 数据集与 Baseline

论文使用了若干真实或半真实的数据集，包括 YouTube-8M / YT5M、YFCC 等带标签数据，以及大规模合成或扩展数据。

对比方法包括：

- 基于 PipeANN 的 pre / post 策略组合；
- WASS / Milvus 一类依赖 cost model 选择 pre 或 post 的方法；
- 经典 in-filtering 方法；
- PipeANN-Filter 自身的混合策略。

从录音讨论看，实验部分存在一些不够清晰的地方：例如 query 是否真实、label 是否与向量原始数据强相关、range value 如何构造、不同数据集的标签分布统计等，论文中似乎没有给出足够完整的说明。

### 整体性能

论文整体声称 PipeANN-Filter 在多个数据集上优于 baseline，尤其是在能够正确选择 pre / in / post 策略时表现较好。

但不同数据集上的结果差异比较明显。例如某些数据集上大量 query 最终选择 post-filtering，而 post-filtering 本身并不是 PipeANN-Filter 的主要新增机制，这会让系统收益的解释变得不够直接。

在 YFCC 等数据集上的表现似乎也更接近某些 baseline，论文给出的解释和结果之间存在一定疑问。录音中也提到，实验可能更像阶段性版本，baseline 和数据分析还不够充分。

### Cost Model 的准确性

论文还分析了 cost model 的估计误差。

在某些数据集上，估计成本与真实成本接近；但在更大规模或分布更复杂的数据集上，估计偏差会明显变大。

一个可能原因是：模型使用选择率 $s$ 去近似需要探索的候选数量，但真实图搜索还受到标签与向量空间联合分布的影响。

如果标签在向量空间中均匀分布，那么 $L / s$ 近似可能还算合理；如果标签强烈成团，搜索一旦进入相关区域，可能很快找到大量有效节点；如果标签分布和向量距离高度错位，搜索成本又会显著上升。

因此，单纯依赖统计公式做策略选择可能不够稳健。一个更工程化的替代方案是：离线 profiling 不同选择率、不同标签类型、不同 query 分布下的真实性能，再用经验阈值或轻量模型做在线选择。

### 假阳性比例与内存权衡

推测性过滤的核心代价是假阳性。

录音稿中提到，在某个 100M 级数据集上，假阳性节点比例可能达到 60%，而其他数据集上通常在 20% 以下。假阳性过多会导致两个问题：

- 大量无效节点进入候选池，挤占真正有效节点的位置；
- 额外 SSD 读取和距离计算增多，抵消近似过滤带来的收益。

这与 Bloom Filter 或 range bucket 的大小直接相关。为了节省内存，结构做得越小，假阳性率就越高；如果增大 Bloom Filter 或提高 range bucket 精度，内存占用又会上升。

因此，PipeANN-Filter 本质上是在“内存占用、误判率、I/O 开销、搜索质量”之间做权衡。

## 讨论与思考

### 1. 推测性过滤的价值

推测性过滤是这篇工作的核心亮点。它不是简单地把过滤条件做成硬约束，而是允许“可能有效”的节点参与搜索，再在最终结果阶段做精确验证。

这个思路很适合 SSD 图索引，因为图搜索需要连通性。低选择性过滤下，如果过早丢弃不满足条件的节点，可能导致搜索路径断掉；保留一部分假阳性节点，反而能起到桥接作用。

### 2. Range filter 设计偏粗

Range filter 使用 1 Byte / 256 桶的方案实现简单，但精度可能不足。对于范围过滤，如果查询区间很窄或数值分布高度倾斜，粗桶会带来大量假阳性。

可以考虑的改进包括：

- 根据属性分布自适应划分桶，而不是简单等宽压缩；
- 对高频范围或热点属性使用更细粒度编码；
- 针对不同属性设置不同 bucket 数，而不是统一 256 桶。

### 3. Cost Model 可能不如离线 profiling 稳定

在线 cost model 看起来很灵活，但它依赖很多假设：选择率估计、假阳性率估计、标签分布、图搜索早停行为等。

如果索引和数据集是相对静态的，离线测量不同策略在不同选择率区间的真实性能，可能更直接、更稳定。很多混合过滤系统其实都会采用类似的经验阈值策略。

### 4. 数据集分析很重要

录音讨论中反复提到一个点：带标签的向量数据集不只是“向量 + 标签”这么简单，标签和向量空间之间可能存在很强的联合分布关系。

例如，文章分类标签往往和语义向量聚类高度相关；图片或视频标签也可能呈现明显的类别聚集。此时 label 近的点可能 vector 也近，vector 近的点也可能共享 label。

这种相关性会直接影响过滤 ANN 的设计：

- 如果标签在向量空间中成团，图搜索可能更容易找到满足条件的区域；
- 如果标签高度分散，则需要更强的过滤索引或桥接机制；
- 高频标签和低频标签的长尾分布，也会影响 Bloom Filter、倒排索引和策略选择。

因此，在做过滤向量检索系统时，对真实数据集的标签频率、标签-向量相关性、range value 分布做系统分析，本身就是很有价值的工作。

## 总结

PipeANN-Filter 面向 SSD 上的过滤 ANN 搜索，主要贡献可以概括为：

1. 用推测性过滤替代严格过滤，允许假阳性节点参与图遍历，从而缓解过滤导致的连通性问题；
2. 同时支持 label filter 和 range filter，并分别用 Bloom Filter、倒排索引和桶化数值编码实现近似判断；
3. 在 pre-filtering、in-filtering 和 post-filtering 之间建立 cost model，根据查询动态选择策略；
4. 针对 in-filtering 引入二跳邻居等机制，提升低选择性下的可达性。

从工程角度看，这篇工作的方向是有意义的：SSD 场景下 I/O 成本很高，过滤搜索必须同时考虑图连通性、属性判断成本和最终结果正确性。

但它也留下了一些值得继续验证的问题：实验数据集和 query 构造需要更清晰，range filter 的桶化设计偏粗，cost model 在复杂分布下可能不够稳健，假阳性比例与内存开销之间也需要更系统的权衡。

整体来说，PipeANN-Filter 更像是把 SSD ANN、过滤检索和混合策略选择整合到一个统一框架里。它提供了一个有启发性的方向，但真正落地时，还需要结合具体数据分布做更细的 profiling 和参数调优。
