## 前言

在真实的向量检索系统里，用户通常不只是想找“语义上最相似”的向量，还会同时带上一些结构化过滤条件。例如：

- 在电商搜索里，用户可能想找“红色、价格 100 元以内、风格相似”的衣服；
- 在图片检索里，用户可能只想搜索某个时间范围、某个地点、某类标签下的图片；
- 在推荐或广告系统里，候选向量也常常需要满足业务标签、权限、时间窗口等约束。

这类问题通常被称为 **带过滤条件的 ANN 搜索**（Filtered Approximate Nearest Neighbor Search）。它的难点在于：过滤条件可能非常稀疏，也就是满足条件的向量只占全集中极小的一部分。Curator 关注的正是这种 **低选择性过滤** 场景。

本文整理自论文分享录音稿，主要介绍 Curator 想解决什么问题、为什么现有方法在低选择性下效果不好、它的双索引架构如何设计，以及实验中体现出的性能与代价权衡。

## 背景与动机

### 带过滤的 ANN 搜索

传统 ANN 搜索只关心向量距离：给定查询向量 $q$，从数据集中找到距离 $q$ 最近的若干个向量。

Filtered ANN 则多了一层约束：候选向量不仅要距离近，还必须满足某些标签或谓词条件。形式上可以理解为：

> 在满足过滤条件 $P(x)$ 的向量集合中，找到与查询向量 $q$ 最近的 top-k 结果。

这里的过滤条件既可以是单标签，例如 `color = red`，也可以是复杂谓词，例如多个标签之间的 AND / OR 组合，甚至可以把时间、价格等范围条件离散化后视为多标签过滤。

过滤条件的 **选择性** 指满足过滤条件的向量比例。选择性越低，说明符合条件的向量越稀疏。例如选择性为 0.001，意味着只有千分之一的数据满足过滤条件。

### 低选择性过滤的挑战

低选择性场景对现有 ANN 方法非常不友好。论文主要讨论了几类方法的局限。

#### 1. 直接暴力过滤

最简单的做法是先过滤出所有满足条件的向量，再在这些向量上做精确搜索或近似搜索。

这种方法实现简单，但在大规模数据上代价很高。如果每次查询都需要扫描大量元数据或候选向量，查询延迟很难接受。

#### 2. 图索引在低选择性下会出现连通性问题

HNSW、DiskANN 等图索引依赖图上的邻居连接来逐步逼近查询点。但加入过滤条件后，图里很多节点虽然在向量空间上有用，却不满足过滤条件。

在低选择性下，满足条件的节点非常少，合格节点之间的连接可能非常稀疏，甚至被不合格节点隔开。这会造成两难：

- 如果搜索时允许经过不合格节点，就会访问大量无效邻居，计算代价很高；
- 如果完全跳过不合格节点，图的连通性可能崩溃，导致召回率下降。

一种补救思路是给图增加更多边，让同一标签下的合格节点也保持连通。但随着选择性降低，为保证每个节点都有足够的合格邻居，总度数会快速膨胀。论文中给出的直觉是：如果每个节点希望拥有 $m$ 个合格邻居，而过滤选择性为 $s$，那么平均需要检查或维护约 $m / s$ 级别的连接，低选择性时成本会非常高。

#### 3. 分区索引会访问过多聚类

IVF、层次聚类树这类分区索引没有图连通性问题，但在低选择性下也会遇到另一个问题：每个细粒度分区里可能只有很少甚至没有合格向量。

为了找到足够的结果，查询必须访问更多分区，并和更多聚类中心做距离计算。也就是说，虽然候选向量本身很少，但为了定位这些稀疏向量，索引遍历开销反而变大了。

### Curator 的核心想法

Curator 的目标是补足现有方法在低选择性过滤下的短板。它采用一种基于分区的双索引架构：

1. 用一棵共享的基础索引对全量向量做层次化空间划分；
2. 针对每个标签，在共享基础索引上嵌入一个轻量的标签索引；
3. 对复杂谓词，不提前穷举所有组合，而是在查询时基于合格向量 ID 快速构建临时索引。

关键直觉是：**标签越稀疏，就越不应该被迫走到很深的叶子节点。** Curator 会把稀疏标签对应的合格向量缓存在更高层级的节点中，使查询只访问少量高层节点就能拿到候选向量；标签越稠密，才需要继续向更细粒度的分区下探。

## 核心设计

### 整体架构

Curator 的设计可以分成三部分：基础索引、单标签索引和紧凑编码。

#### 基础索引：共享的层次化 k-means 树

基础索引是一棵标准的层次化 k-means 聚类树。它对全量向量做空间划分，每个节点代表一个聚类区域，子节点表示更细粒度的空间切分。

这种结构有两个好处：

- 它不像图索引那样依赖合格节点之间的连通性，因此低选择性不会天然破坏搜索路径；
- 层次化结构天然支持不同粒度：稀疏标签可以停留在较高层，稠密标签可以继续下探到较深层。

换句话说，基础索引提供的是一副全局共享的“空间骨架”。不同标签不需要各自重新聚类，而是复用这副骨架，在其上构建自己的逻辑视图。

#### 单标签索引：嵌入在基础索引上的逻辑子树

对于某个特定标签，Curator 不会重新建立一棵完整的物理树，而是在基础索引上构建只包含该标签合格向量的逻辑子结构。

这个单标签索引并不要求和基础索引每一层完全一一展开。它会根据该标签在空间中的密度自适应决定在哪里停止：

- 如果某个基础索引节点下，符合该标签的向量数量不多，就直接把这些向量 ID 存入该节点的 buffer，并把这里视为标签索引的叶子；
- 如果符合该标签的向量太多，说明这个区域仍然稠密，需要继续沿基础索引的子节点向下划分。

因此，所谓“嵌入式标签索引”可以理解为：它复用了基础索引的父子空间关系，但只保留和当前标签相关的路径，并在合适的层级缓存合格向量 ID。

需要注意的是，标签索引中的父子关系不是简单的“父节点 buffer 包含子节点 buffer”的关系。因为一旦某个节点已经用 buffer 存下了足够少的合格向量，就不再需要继续向下展开；而如果继续向下展开，则说明该节点自身不直接作为最终候选 buffer。

#### 紧凑编码：buffer 与 Bloom Filter

为了降低内存开销，单标签索引不存储真实向量数据，而主要依赖两类结构。

第一类是 **buffer**。buffer 存在于标签索引的逻辑叶子节点中，里面保存排序后的合格向量 ID。查询访问到这样的节点时，可以直接对 buffer 内的向量做精确距离计算。

第二类是 **Bloom Filter**。Curator 会在基础索引的节点上维护布隆过滤器，用来近似判断该节点子树下是否可能包含某个标签的向量。

Bloom Filter 的作用是快速否定：

- 如果它判断“没有该标签”，则该子树一定没有，可以直接剪枝；
- 如果它判断“可能有该标签”，则继续搜索，但可能存在假阳性。

这种设计让 Curator 能够快速跳过大量与过滤条件无关的空间分支。

### 单标签查询流程

针对单标签过滤，Curator 的搜索大致分为两个阶段。

#### 第一阶段：beam search 初始化候选队列

查询从根节点开始，在高层聚类树上做 beam search，并维护一个宽度为 $b$ 的候选队列。

这样做是为了缓解高层聚类中心不够精确的问题。如果只沿着距离最近的一条路径下探，可能因为聚类边界误差而陷入局部最优。保留多个有希望的候选节点，可以提高容错率。

例如查询点可能位于两个聚类边界附近。从质心距离看，它似乎更接近一个小聚类；但真实最近向量可能在另一个更大的聚类边缘。beam search 能够避免过早放弃这类有潜力的区域。

#### 第二阶段：best-first search 结合标签剪枝

初始化候选队列后，Curator 继续执行 best-first search。

遍历每个候选节点时，它会先利用 Bloom Filter 判断该节点下是否可能存在目标标签：

- 如果 Bloom Filter 判断不存在，直接跳过整棵子树；
- 如果可能存在，则继续访问。

当搜索遇到带 buffer 的逻辑叶子节点时，就计算 buffer 内所有合格向量与查询向量的精确距离，并更新结果集。

搜索终止条件可以理解为：当继续扫描新的 buffer 已经不能改善当前结果集时，搜索收敛并停止。

### 启发式评分函数

Curator 在选择下一个要访问的节点时，不只看查询点到聚类质心的距离，还引入了聚类半径因素。论文中的启发式评分可以概括为：

> 节点得分 = 查询点到簇质心的距离 - 与簇半径相关的修正项。

其中半径项由参数控制，用来给“范围更大、虽然质心略远但边缘可能更接近查询点”的聚类一些额外机会。

这个评分函数的意义是：不要只盯着质心最近的小区域，也要探索那些覆盖范围较大、潜在包含近邻的区域。它让搜索策略更接近“有希望的空间区域优先”，而不是简单的“质心距离最近优先”。

### 复杂谓词查询：查询时构建临时索引

单标签索引可以提前构建，但复杂谓词组合几乎是无限的。如果为所有 AND / OR 组合都预先建立索引，内存和构建成本都会不可接受。

Curator 的做法是：对于复杂谓词，先得到满足谓词的合格向量 ID 列表，再在查询时快速构建一棵临时索引。

这个临时索引仍然复用基础索引的空间拓扑。关键在于 Curator 对节点 ID 和向量 ID 做了编码，使有序向量 ID 天然带有空间区间信息。

#### NID 与 VID 编码

在基础索引树中，每个节点都有一个 NID（Node ID）。NID 可以看作从根节点到当前节点所经过的分支序列编码，因此它记录了该节点在层次聚类树中的空间拓扑位置。

每个向量也有一个 VID（Vector ID）。VID 可以由叶子节点的 NID 加上该向量在叶子节点中的局部偏移打包得到。

这意味着：VID 的高位部分隐含了该向量属于哪个叶子节点，也就隐含了它所在的空间区间。

如果把满足复杂谓词的 VID 排序，那么属于同一个空间分支的向量在数组中会自然连续排列。Curator 正是利用这一点快速构建临时子树。

#### 临时索引构建过程

临时索引构建可以概括为递归过程：

1. 从基础索引根节点和完整的合格 VID 有序列表开始；
2. 如果当前列表大小不超过 buffer 容量上限 $B_{max}$，说明当前区域已经足够稀疏，直接创建一个带 buffer 的临时叶子节点；
3. 如果列表大小超过 $B_{max}$，说明当前区域仍然太稠密，需要继续沿基础索引的子节点拆分；
4. 对每个子节点，根据其负责的 VID 区间，在有序列表中通过二分查找定位左右边界；
5. 如果该子节点区间内存在合格向量，则递归构建对应子树；
6. 所有子树构建完成后，将它们挂到当前临时节点下并向上返回。

这个过程的代价很低，因为它不需要重新聚类，也不需要扫描全量数据，只是在有序的合格 ID 列表上按基础索引的空间区间做切分。

更重要的是，它避免了复杂谓词组合爆炸：系统不需要提前存储所有组合索引，而是在查询到来时按需生成一个轻量的虚拟树。

## 实验评估

### 实验设置

论文的实验实现基于 C++ 和 FAISS，使用 Float32 表示向量，没有使用标量量化或乘积量化，从而排除了量化误差对召回率的影响。

实验主要使用两个数据集：

- **YFCC-10M**：约 1000 万向量，192 维，约 1000 个不同标签，平均每个向量 5 个标签；
- **Active**：约 200 万向量，384 维，约 100 个不同标签，平均每个向量 9 个标签。

对比方法包括经典向量索引变体、过滤专用图索引、关系型数据库扩展以及直接 pre-filtering 等退化基线。

### 单标签过滤性能

在不同低选择性单标签过滤器上，论文比较了召回率和查询吞吐量之间的关系。

整体来看，Curator 在多组选择性下都处于较优的 recall-QPS 权衡位置。虽然某些方法在个别数据集或指标上能取得更高 QPS，例如 per-label HNSW 或某些 IVF 变体，但这些方法往往需要为每个标签维护独立索引，内存消耗和构建成本很高。

Curator 的优势在于：它的搜索性能具有竞争力，同时额外内存和构建成本明显更低。因此它不是单纯追求某个点上的最高吞吐，而是在性能、内存和构建时间之间取得更好的工程平衡。

### 复杂谓词性能

复杂谓词是 Curator 表现更突出的场景。

论文中比较了预先建立组合索引的方法、查询时构建临时索引的 Curator 版本，以及先进的过滤图索引基线。结果显示，查询时临时构建索引的 Curator 能接近预构建索引的性能，并且在 AND / OR 等过滤组合上显著优于过滤图索引基线。

这说明临时索引构建并没有成为瓶颈。由于 Curator 复用基础索引拓扑，只需要对排序后的合格 VID 做区间切分，它能够以很小的代价获得一棵适合当前复杂谓词的虚拟树。

这也是 Curator 相对于许多现有方法的“降维打击”：其他方法要么无法自然支持复杂谓词，要么必须预先构建大量组合索引；Curator 则把组合复杂度推迟到查询时，并用轻量构建过程消化掉。

### 资源消耗

论文还比较了不同方法的索引构建时间和内存净开销。

Curator 在这两个指标上都比较低。相比 per-label HNSW、per-label IVF 等方法，它避免了为每个标签复制完整索引结构，因此构建时间和内存开销更可控。

有些磁盘或紧凑反向列表方案的内存占用可能更低，但搜索性能明显逊色。Curator 的定位不是极限压缩内存，而是在少量额外资源下提供接近最优的查询性能。

综合来看，Curator 在“索引开销、构建时间、查询延迟”三者之间处在较优位置，尤其适合对内存容量和构建时间有要求、但又需要处理低选择性过滤查询的系统。

### 动态更新与扩展性

Curator 还支持比较完整的动态更新，包括：

- 向量插入；
- 向量删除；
- 标签插入；
- 标签删除。

很多图索引方法并不完整支持动态删除，而 Curator 因为基于分区和轻量标签结构，在更新支持上更灵活。论文结果显示，它在多类更新操作上的延迟都较低，并且在向量插入等操作上比共享图索引快很多。

在标签数量扩展性方面，Curator 的内存 footprint 随标签数增长并不剧烈，体现出较好的内存效率。这来自它对基础索引的共享，以及标签索引只存储紧凑 ID 和必要过滤结构。

### 消融实验

论文还做了几个消融验证。

第一是 **结构约束**。Curator 的标签索引强制复用基础索引的空间骨架，而不是为每个标签重新学习最适合自己的聚类中心。实验中，无约束版本和 Curator 的性能曲线几乎重合，说明这种结构约束对索引质量影响很小，却显著降低了实现和存储成本。

第二是 **数据分布鲁棒性**。论文比较了原始数据集和随机打乱数据集下的吞吐-召回权衡，结果基本一致，说明 Curator 对不同数据分布具有稳定表现。

第三是 **规模扩展**。随着数据规模从 200 万增长到 1000 万，遍历开销占比反而有所下降。这表明 Curator 的额外遍历成本在更大规模下仍然可控。

## 总结与思考

Curator 解决的是低选择性过滤 ANN 搜索中的一个核心矛盾：满足过滤条件的向量很少，但为了找到它们，传统索引往往需要付出很高的遍历、连通性维护或内存复制成本。

它的方案可以总结为三点：

1. **共享基础索引**：用一棵层次化 k-means 树承载全局空间划分，避免每个标签重复建完整索引；
2. **自适应标签索引**：根据标签稀疏程度决定索引深度，稀疏区域在高层节点用 buffer 缓存合格向量 ID；
3. **查询时临时索引**：对复杂谓词按需构建轻量虚拟树，避免预构建所有组合索引带来的爆炸式成本。

从实验看，Curator 在单标签低选择性过滤下有竞争力，在复杂谓词场景下尤其突出，并且索引构建时间、内存开销和动态更新能力都比较适合工程落地。

如果进一步扩展，我觉得可以考虑在高并发场景中为复杂谓词引入缓存机制：对于频繁出现的谓词组合，不必每次都重新构建临时索引，而是缓存其虚拟树或中间 ID 列表，在内存预算允许的情况下进一步降低查询延迟。

总体而言，Curator 的价值不在于替代所有 ANN 索引，而是与高选择性场景下表现良好的图索引形成互补：高选择性时继续使用图索引，低选择性时切换到 Curator 这类分区式过滤索引。至于切换阈值，可以通过离线分析或采样估计来确定。
