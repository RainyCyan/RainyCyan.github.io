## TL;DR

- **KV Cache 本质是一项成本优化技术**：用存储和网络去换 GPU 算力。随着模型 scaling up、序列越来越长、参数越来越大，这部分开销也越来越大。
- **搜广推场景比大模型推理更复杂**：这里有大量泛化场景——用户长序列 KV Cache 的跨刷复用、FM→VM（Foundation Model 到 Vertical Model）的知识迁移、搜索 doc KV Cache 等，规模更大、玩法更多。
- **存储侧核心诉求是低延迟 + 高吞吐**：MB 级 KV Cache 大多要求 P99 在 200ms 左右，GB 级 P99 在 400ms 内；同时要尽可能打满客户端网卡，因为做了 KV Cache 之后后续计算量下降，对网卡的需求反而更大。
- **一致性与防穿越是训练侧的硬约束**：冻结参数 vs 边训边写两类玩法，分别对应「效果衰减」和「模型参数穿越」两类问题，需要按请求时间做序列过滤与参数版本过滤。
- **存储架构以「RDMA 直读直写 HDFS/bytestore」为主推**：最简 IO 路径、单份存储无冗余、中间链路只有一跳 RDMA，把存储和网络成本压到最低；配合分桶并行、智能流控、GPU 解压等手段打满网卡。
- **演进方向**：更激进的压缩、EC 纠删码 / QLC 高密机型 / 冷热分层降存储成本、多场景存储方案标准化（与 USDB 序列存储协同）、生命周期管理与可观测性。

## 1. 为什么搜广推也需要 KV Cache

KV Cache 已经是大语言模型推理的一项必备技术。搜广推场景同样应用了大量大模型推理相关的优化技术，同时 GR（Generative Recommendation）这类模型也在做一些新的范式探索。随着模型 scaling up、序列越来越长、参数越来越大，整体的成本开销也水涨船高。

一句话概括 KV Cache 的定位：**它本质上是一项成本优化技术，用存储和网络来换 GPU 算力。**

而搜广推场景比大语言模型的推理场景更加复杂，这里有很多泛化的场景，例如：

- 用户长序列 KV Cache 的跨刷复用；
- FM（Foundation Model）到下游 Vertical Model 的知识迁移；
- 搜索侧的 doc KV Cache。

这些场景的需求更复杂、规模更大，应用范围也在逐渐变多。后文会逐一展开。

## 2. KV Cache 基础回顾

KV Cache 里的 K、V，指的就是 Transformer 的 attention 机制里 Q/K/V 中的 Key 和 Value。这里有几个关键点：

- **计算复杂度与序列长度的平方成正比**：序列越长，计算开销上涨得越夸张。
- **只需要缓存 K 和 V，不需要缓存 Q**：Q 只属于当前 token，而 K、V 会被后续所有 token 共享。自回归生成下一步时，需要前面所有步的 K、V 做 attention，所以把 K、V 缓存下来可以大量避免重复计算。
- **天然支持 cross-request 复用**：在大模型推理里，是多轮对话、历史前缀共享的场景可以复用；而在推荐场景里有一个天然优势——**用户的历史行为序列是固定的**，所以对这种长序列做 KV Cache，几乎每一次都可以复用，因为前缀是一样的。

### 2.1 存储规模估算

复用的代价是存储规模巨大：我们对每个用户都要存一个很长的序列所对应的 KV Cache。大小可以这样估算：

```
KV Cache 大小 ≈ Token 数 × 层数 × 隐藏维度 × 2（K、V 两份）× 每元素字节数
```

典型场景下单份大约是 40MB 量级。而推荐场景里序列长度可能做到几万甚至 100K 量级，所以**单个用户的 KV Cache 就可能到 GB 级别**，总存储量非常大。

### 2.2 压缩手段

因此压缩非常重要，常见的几类方向：

- **量化**：比如 INT4，甚至进一步做到 INT2；
- **无损压缩**：针对数据分布特点，大概能有 70%~80% 的压缩率；
- **算法侧优化**：像 Sliding Window Attention、Sparse Attention——多层 KV Cache 中只有少量层存储完整序列，其他层只存较短的一段，也能带来很大的压缩。

## 3. 搜广推的三类典型 KV Cache 场景

### 3.1 推理跨刷复用（以 GR 两阶段模型为例）

以抖音 GR 的两阶段模型为例。它有一个仿真 model（Foundation Model），流程大致是：

1. 仿真 model 先完成训练，把参数冻结，打一个模型 checkpoint；
2. 再做一次离线推理，生产一份 **full KV Cache**——它对应用户历史的超长行为序列（10 万级长度）；
3. 在线推理时读取这份 full KV Cache；同时用户会有增量序列，这部分会生成新的 **inter（short-term）KV Cache**；
4. 这两部分 KV Cache 都存储在我们提供的 KV Cache 存储方案里。下一次请求过来时，同时读取这两部分，生成新的 KV Cache，再写回存储。

这里面有很多推理层面的性能与流程优化，例如：

- 在 GPU 机器上先做 **prefetch**，释放延迟空间；
- 数据拿到后先做 **prefill**，等 candidates 到达后再做 **decode**；
- 体系结构层面还有很多针对网络、内存带宽的优化（详见后文存储方案）。

### 3.2 FM → VM 的知识迁移

FM 指仿真 model（Foundation Model），VM 指下游的 Vertical Model（不同业务也叫 Task Model / Downstream Model）。这本质上是一种**两阶段训练范式**，需要做 FM 到 VM 的知识迁移。迁移方式有多种：蒸馏、user embedding 共享，或者 FM 生成类似 KV Cache 的产物传递给下游 VM 复用。

范式大致是：

1. **一阶段**训练 Foundation Model，生产大量 KV Cache 产物。写入方式可以是整体替换（`put`），也可以是 `append`——因为 KV Cache 数据的 token 与序列是一一对应的；
2. **二阶段**训练下游的 Vertical Model，每个 VM 都读取同一份 FM 生成的 KV Cache 数据。

这带来两个特点：

- **一份数据、多份下游模型读**：随着下游模型增多，读带宽会被放大，对存储的性能密度要求很高；
- **跨机房同步**：这份数据还需要做训练机房到推理机房的同步，因为推理阶段也需要同样的数据。

### 3.3 搜索 doc KV Cache

doc KV Cache 用于相关性计算，以降低推理计算量。doc 侧信息较长、query 较短，相当于把两者拼接起来做一次相关性计算，其中 doc 这部分就可以用 KV Cache 来加速。

流程是：在线推理时读取 KV Cache，可能会 **miss**（这部分 KV Cache 可能还没写入）；miss 之后生成 KV Cache，再回写到存储中。这里会对总 cache 大小做控制，支持 **TTL** 和 **FIFO** 淘汰策略——FIFO 指空间满了之后自动淘汰最老的数据，释放空间给最新数据写入。我们也在进一步探索冷热分层等技术。

## 4. 存储侧的典型需求

### 4.1 低延迟

目前看到的一些场景：

- **MB 级 KV Cache**：大部分要求 P99 在 200ms 左右；
- **GB 级 KV Cache**：P99 要在 400ms 内。

### 4.2 高吞吐

高吞吐与低延迟放在一起是很大的挑战。高吞吐意味着要**尽量打满客户端网卡的上限**，才能充分利用算力。

这里有一个比例关系：每份数据对应一定的 GPU 算力消耗。当 GPU 算力是瓶颈时，对网卡的需求会变少；但我们看到很多场景做了 KV Cache 之后，后续计算量下降，**反而对网卡的需求量非常大**，需要尽可能打满后端 GPU 机器的网卡。

### 4.3 数据连续性与一致性

推理需要对新序列做增量 `append`（short-term KV Cache），因此涉及：

- 数据连续性校验与一致性需求；
- 并发冲突处理：一般对同一个 uid 做**一致性哈希**，让它尽量落到同一台机器上；
- 长短时效并存：也有一些短时效 cache 场景，比如 TTL 是小时级别的 cache。

### 4.4 训练侧的高吞吐与防穿越

- **多读高吞吐**：FM→VM 场景下游模型多读，当 VM 模型非常多时，对存储的性能密度要求会大幅增加；
- **防穿越**：训练时下游每个模型的样本进度不一样，可能在训练历史样本，必须通过样本时间做过滤，避免用到未来的、可能穿越的数据。

## 5. 一致性与防穿越的两类玩法

核心目标是避免**模型参数导致的不一致或穿越问题**。业务上有两类场景：

### 5.1 冻结参数

先训一个仿真 model，将参数冻结、打 checkpoint，然后用冻结的参数做批量推理生产 KV Cache。

- **优点**：参数一致（都是冻结后的），基本不会发生模型参数的不一致或穿越问题；
- **缺点**：随着时间推移效果会有一定衰减，因为参数是冻结的，不感知最新的数据分布。

### 5.2 边训边写

仿真 model 一边训练一边写出 KV Cache，模型参数不断变化。

- **问题**：不同时间生产的 KV Cache，即使是对同一份序列，也会有很大差异；因此**参数变化后无法重算**——重算的效果和第一次不一致；
- **防穿越做法**：需要根据请求时间做两方面过滤——
  1. **序列过滤**：过滤掉未来的序列；
  2. **参数版本过滤**：检查这份 KV Cache 对应的模型参数时间是不是更老的，避免模型参数导致的穿越。

## 6. 当前的存储方案

### 6.1 模块划分

- **KV Cache SDK**：部署在用户的 GPU 机器上（推理和训练都有），与用户进程连编；
- **服务端模块**：Meta 配置管理、KV Cache 的 value meta 存储（正排）、控制节点；
- **数据存储**：存在 HDFS 或 bytestore 集群上，数据打散分布在不同 DN 上。KV Cache 总规模很大，可能到几 PB 甚至几十 PB，需要很大的集群来存储。

### 6.2 主推架构：RDMA 直读直写

目前主推的架构，是通过 KV Cache SDK 做**数据的直写、直读**，尤其针对 size 大、吞吐要求高的场景，做到**最简 IO 路径**：

- 只读只写 HDFS，通过 **RDMA** 访问，减少中间链路；
- 本质是降低存储和网络成本——数据只存在 HDFS/bytestore 一份，**没有冗余存储**；可以通过优化机型、副本数、冷热分层、多集群混部等方式尽可能降本；
- 中间链路的 TCE 节点成本很低：机器数很少，网络上只有一跳 RDMA。在大吞吐场景下减少中间交换机的开销尤为重要——否则大流量再经过中间一跳会额外增加很多成本，网络压力也很大。

### 6.3 数据模型与接口

分两类模型：

- **支持 append 的长序列模型**：一个 uid 下的 KV Cache item 可以 `append` 组合，也支持 `put` 覆盖；读取时支持只返回其中某些 item（减少网络带宽），也支持按时间过滤（避免一致性 / 穿越问题）；
- **KV 模型**：一个 key 只对应一个 KV Cache item，做整体读写。

元数据单独存储，可以按字段过滤来按需读取、减少带宽。

**KV Cache item 是一个相对抽象的结构**，支持业务采用不同的打包方式：

- **整体打包**：对一段序列对应的 KV Cache 整体打包；
- **分层打包**：按模型的不同层来打包；
- **分层分段打包**：每一层内进一步拆成多段，每段是一个 item。可以按层过滤、每层只读某一段，过滤更灵活，进一步减少网络传输。

### 6.4 数据流程

以推理场景为例：

1. **离线生产**：离线任务把模型推理产生的原始 KV Cache 直接写入 HDFS/bytestore（只写），写完后再把少量 Meta 信息通过正排写入 Meta 集群；
2. **实时推理**：通过 RDMA 只读 HDFS。如果做了 uid 路由，很多 cache 可以做在 GPU 机器的进程内（uid cache、meta cache），从而避免读取正排、直接知道数据位置；
3. **增量写**：同样通过直写方式写到 HDFS，写成功后再更新元数据集群。

读取时支持多种模式：

- 全量读取一个 uid 下的所有 KV Cache 数据；
- 通过元数据过滤 / 筛选，或仅用来判断 KV Cache 是否存在；
- 获取 KV Cache 中的某些字段，用来判断是否需要读原始序列，做一些提前的判断和设计；
- 筛选读：只读某个 uid 下的部分 KV Cache。

## 7. 性能优化

### 7.1 分桶并行 + 智能流控

为了尽可能打满客户端网卡，内部会做**并发访问、分桶并行读取**。分桶并行后要避免一个问题：网络拥堵时很多请求分散在很多桶里，不能因为部分子请求失败就影响整体成功率。

因此内部做了**智能流控**：在网络打满时不引发雪崩，而是只控掉个别请求，让能成功的请求尽量整体成功。这些子请求还可以有优先级——比如靠下的层、比较早的数据可以给更高优先级。

### 7.2 RDMA + 多网卡

我们打通了 RDMA 网络链路，和 HDFS 存储团队、高性能网络团队一起协作，利用 **RDMA + 多网卡** 充分利用网络。推理场景目前使用的是 **200G × 4** 的大网卡机型（L20）。

相比纯 TCP，TCP 有很大的瓶颈——包括内存带宽瓶颈以及内核网络自身的瓶颈；RDMA 下可以得到很大缓解和提升。

### 7.3 内存带宽优化与 GPU 解压

随着网卡不断提升，**内存带宽瓶颈非常凸显**，中间过程要尽量避免拷贝。

数据本身做了无损压缩（约 80% 压缩率）。如果在 CPU 端做 ZSTD 解压，对 CPU 和内存带宽都有损耗，在极高网卡压力下这部分瓶颈会非常明显。因此我们做了 **GPU 解压**：通过 GPU 内一个优化过的 ANS 解压算法，在 GPU 内高效解压，从而达到更高的整体吞吐。

### 7.4 性能瓶颈分析

一般从两方面分析：

- **GPU 机器侧**：带宽瓶颈与算力瓶颈的比例、内存带宽消耗、是否需要通过 GPU 解压进一步优化；
- **服务端**：单位 TB 对应多大带宽。对存储机型来说也分存储瓶颈和网络瓶颈——盘数很多时，往往网络瓶颈比盘的瓶颈更先达到，所以大多是存储瓶颈与网络瓶颈之间随 pattern 变化的转化关系。

在 cache 方面：

- 做了 uid 路由或其他 key 路由后，可以做**本地 cache**：先读本地、再读远端。一般通过估计能 cache 住 top 百分之多少的热数据，来计算覆盖了多少 QPS，从而推算带宽优化比例；
- **训练侧的多任务共享 cache**：训练机器分机头网络和机尾网络——机头网络可访问远端存储，机尾是 GPU 机器单独组的 HPN 网络，不能访问远端存储。多任务共享 cache 可以充分利用机尾的 RDMA 网络。

## 8. 未来演进方向

### 8.1 持续降低存储成本

- **更高压缩率**：探索更激进的有损 / 无损压缩方式；
- **EC 纠删码**：目前 HDFS 大部分是两副本；EC 常用配置如 `4+2` 可做到约 1.5 倍、`8+3` 约 1.375 倍，比例优化很可观；
- **QLC 高密机型**：很多场景是容量瓶颈而非带宽瓶颈，非常适合高密存储——QLC 单机约 500T 容量，单位 TB 成本比普通 S80 SSD 低很多；
- **冷热分层 + 多集群混部**：把容量瓶颈、带宽瓶颈、盘 OPS 瓶颈不同的集群做业务上的混部，充分利用之前无法利用的资源，同时做数据的快速淘汰。

### 8.2 多场景适配的方案标准化

搜广推场景下 KV Cache 有很多泛化需求，可以做一定程度的存储方案统一，并与整体序列存储方案 **USDB** 做协同设计——因为有些 KV Cache 场景在做了各种优化后，size 可以控制在单 uid MB 级，和长序列的 size 相对接近，可以统一掉一些方案。同时提供 Python 接口简化接入，支持内置的量化、压缩和编码优化。

### 8.3 管控与可观测

完善生命周期管理的自动化和质量监测（这是当前很多业务的痛点），并在可观测方面做到更好的能力，以及对成本的分析能力。

## 9. Q&A

**Q1：KV Cache 大小是不是跟序列长度线性相关？**

确实是线性相关。但从算法角度看，序列扩长之后会用更激进的量化 / 压缩手段来控制 size。所以最终结果上，序列扩了 10 倍，KV Cache size 并不会同样扩 10 倍，而是要进一步压缩。

关于「context 超了之后历史序列是否淘汰」：其实历史序列也会淘汰，有两种方式——

1. **读取时截断**：数据还在存储侧，读取时做截断，只读最新的一段（比如 1 万长度），以控制读取的 KV Cache 大小；
2. **定期重刷**：仿真 model 会定期（比如周级）更新模型并整体重刷数据，重刷之后 full 部分和 inter 部分都会被淘汰，被一份更新的 full KV Cache 覆盖。

**Q2：如果不能 prefix、不能匹配呢？本地 cache 到底划不划算？**

从模型角度是有一定解法的，所以并不是一定要严格前缀匹配。

关于本地 cache 是否划算，要看几个因素：

- **命中率**：不同场景差别很大。当 KV Cache 很大时，一些场景实测本地 cache 命中率确实很低，不一定划算；
- **本地可用空间**：主要看 SSD 盘有多大。推理机型本身可能只有一两块盘，整体 cache 效果做不到很高；
- **盘的吞吐**：只有一两块盘时，单盘吞吐大约 3GB/s 左右；相比之下我们进一步扩充网络（现在是 200G × 4），把网络利用好其实有几十 GB/s 的带宽。所以本地 cache 能带来的提升上限比较有限；如果盘挂得比较多，可能会有一定空间。
