## 前言
上下文有限限制了我们在一次会话完成任务的幻想，注意力丢失导致我们在一轮会话也无法很好完成任务；

LLM 本身是无状态的：每次推理都只依赖输入的 prompt，模型并不会"记得"上一次和你说过什么。
但当我们用 LLM 搭建 Agent 时，"记忆"几乎是绕不开的能力——

- 多轮对话里，agent 要记得用户的姓名、偏好、上下文话题；
- 长任务里，agent 要记得自己已经做过什么、剩下什么没做；
- 跨会话里，agent 要记得用户上周提过的项目、踩过的坑、定下的约定。

所以 Agent Memory 的本质并不是给模型加一块"硬盘"，而是一整套围绕 **context engineering** 的系统设计：
**在合适的时机，把合适的信息，以合适的形式，塞进有限的 context window 里**。

这里有两层意思，一个是存信息，也就是“记”；一个是信息检索的触发，也就是“忆”；

## 为什么需要 Memory
最朴素的方案是把所有历史都拼到 prompt 里。但很快会遇到几个硬约束：

1. **Context window 有限**：哪怕是 1M token 的模型，把过去半年聊天全塞进去也是奢侈而低效的。
2. **Attention 是稀释的**：context 越长，模型对关键信息的关注度越容易被噪声稀释，出现 "lost in the middle"。
3. **成本与延迟**：token 越多，单次调用越贵越慢。
4. **跨会话需求**：浏览器关掉、进程重启、换一台机器，对话历史就丢了。

因此我们需要一套机制：能筛选、能压缩、能持久化、能按需召回。这就是 Memory 系统要做的事情。

## Memory 的几种分类
学界和工业界对 Agent Memory 有不同的划分方式，我比较喜欢按"时间维度"和"内容维度"两条线一起看。

这里根据一篇综述和我自己的理解尝试对Agent Memory分一下类：

### 按时间维度
- **Short-term Memory（短期记忆）**：本次会话/本次任务的上下文，通常直接活在 prompt 里。
- **Long-term Memory（长期记忆）**：跨会话、跨任务持久化的信息，通常存到外部存储里，按需检索。

### 按内容维度（借鉴认知心理学）
- **Episodic Memory（情景记忆）**：发生过的具体事件，比如"用户上周让我帮他订过一张去上海的机票"。
- **Semantic Memory（语义记忆）**：抽象出来的事实和知识，比如"用户是 Java 程序员，偏好 Spring 全家桶"。
- **Procedural Memory（程序性记忆）**：怎么做事的经验，比如"这个用户喜欢先看结论再看分析"，或者 agent 学到的 skills、workflows。

###
- token记忆

- latent记忆

- param记忆

不同的产品形态对各类记忆的侧重不同：
- 聊天助手类（如 ChatGPT 的 memory）更依赖 episodic + semantic；
- 编码 agent（如 Cursor、Codewiz）更依赖 procedural + semantic（项目规约、风格、技术栈）；
- 任务型 agent 更依赖 short-term 的执行状态 + long-term 的经验沉淀。

## 一个 Memory 系统通常长什么样
抛开具体实现，一个 memory 系统大致可以拆成四个阶段：

```
[输入] -> [Encode 抽取]  -> [Store 存储]  -> [Retrieve 检索]  -> [Inject 注入]
                                              ^
                                              |
                                       [Update / Forget]
```

### 1. Encode：从对话流里抽出"值得记的东西"
不是所有 token 都值得被记住。常见做法：
- **基于规则**：识别"我叫 xxx"、"我喜欢 xxx"等模式。
- **基于 LLM 抽取**：用一个小模型/同模型在后台跑 summarizer，把对话压缩成结构化的 facts。
- **基于事件**：任务完成、用户显式说"记住这个"时触发写入。

抽取阶段最容易踩的坑是 **过度抽取**：把所有无关闲聊都当成事实存起来，长期看会污染整个记忆库。

### 2. Store：怎么存
常见的三类底座：
- **Key-Value / 文档**：结构化字段，例如 `user.name`、`user.timezone`，适合 profile 类信息。
- **Vector DB**：把片段 embedding 后存起来，支持语义检索，适合海量非结构化记忆。
- **Graph**：用实体-关系来组织记忆，适合需要做多跳推理的场景（比如 GraphRAG、社交关系类应用）。

实际系统里这三者往往是混合使用的：profile 走 KV，长文本走 vector，实体关系走 graph。

### 3. Retrieve：召回
召回策略决定了 memory 用得好不好。常见的有：
- **相似度检索**：当前 query embedding 与历史片段最相近的 top-k；
- **时间衰减**：越近的记忆权重越高；
- **重要性打分**：抽取时给每条记忆打一个 importance score（参考 Generative Agents 的设计）；
- **混合检索**：rerank 多路召回结果。

> Score = α * similarity + β * recency + γ * importance

这个加权公式是 Generative Agents 论文里很经典的设计，今天大量产品仍在沿用。

### 4. Inject：把记忆塞回 prompt
召回出的记忆不是直接 concat 就完事，还要考虑：
- **位置**：放 system prompt 里，还是放在 user 消息前？前者更稳定，后者更新鲜。
- **格式**：用自然语言摘要，还是结构化字段？
- **预算**：给 memory 预留多少 token？超额怎么裁剪？

### 5. Update & Forget：会写也要会忘
这一步常被忽略，但它决定了 memory 系统会不会随时间崩塌：
- **去重**：同一事实多次出现要合并而不是重复存；
- **更新**：用户改了偏好（"我现在用 Rust 不用 Go 了"），老记忆要被覆盖或标记过期；
- **遗忘**：对低频、低重要性、过时的记忆做 decay 或直接删除。

可以类比人脑：你记得清楚的，是反复用到的和情绪强烈的，其他都在慢慢遗忘。

## 几个值得了解的工程实现
- **MemGPT / Letta**：把 LLM 当成 OS，区分 main context 和 external context，引入"分页"思想。
- **Mem0**：开源 memory 层，主打"抽取-存储-召回"的标准化 pipeline，对接 KV + Vector。
- **Generative Agents（斯坦福小镇）**：开创性地提出 reflection + importance score + retrieval 的组合。
- **ChatGPT Memory**：典型的 user-level semantic memory，强调用户可控（可以查看、删除每一条）。
- **Cursor / Codewiz Rules**：本质是 procedural memory 的工程化形态，把"怎么和这个项目相处"以规则文件的形式固化。

## 给做 Agent 的几个实践建议
1. **先不要急着上 vector DB**。很多场景一个结构化 profile + 一段滚动 summary 就够了，引入 vector 之前先想清楚为什么需要它。
2. **把 memory 当作 product feature 来设计**，而不是技术黑盒：让用户能看到、能修改、能删除记住了什么，这关乎信任。
3. **写入要克制，召回要激进**。宁可记少一点准一点，也不要塞一堆噪声；但召回时多路融合、宽召回 + rerank 通常效果更好。
4. **给 memory 加版本和时间戳**。事实是会变的，没有时间戳的记忆迟早会自相矛盾。
5. **观测先于优化**。把每次召回了什么、注入了什么、最终模型用没用都打点出来，否则调优就是玄学。

## 写在最后
Agent Memory 现在还远没有形成标准答案。
不同业务形态需要的记忆是不同的，甚至同一个产品里，不同子能力的记忆策略也不该一样。

我自己更倾向于把它看成 **context engineering 的一个子问题**：
一切都是为了在有限的 context 里，让模型"恰好"知道它该知道的事情——
多一分嫌吵，少一分嫌笨。

## AI 智能体时代的记忆系统

形态、功能与演进。

### 什么是记忆

它并不是普通存储，而是一种支持读写、可演进的状态。

> 智能体记忆不仅保存信息，更参与后续交互、推理与策略更新；
> 强调跨任务持久性，状态可写入、可更新、可被主动调用。

概念对比：

- **LLM 内部记忆**更偏向模型参数、KV Cache 或隐状态的优化；智能体记忆更强调外部支架，以及长期、持续的任务状态。
- **RAG** 面向静态知识检索；智能体记忆则随交互持续生长和更新。
- **上下文工程**关注单次任务信息的即时调度和窗口填充；记忆关注的是智能体生命周期中的长期认知连续性。

### 智能体为什么需要记忆

按承担的功能划分，智能体的记忆通常分成三类：事实记忆、工作记忆和经验记忆。

**事实记忆**回答的是"系统知道什么"。它保存用户偏好、身份、社交关系，以及某一时刻 / 地点 / 人物相关的环境状态——比如当前的工作路径、配置服务器使用的操作系统，这些是不可动摇的客观事实。

**工作记忆**回答的是"系统正在处理什么"。当智能体执行多步复杂任务（比如做一次系统性文献回顾）时，需要一块临时的草稿纸：上一步搜了哪些关键词、剔除了多少篇、目前进行到哪一步。这种与任务紧绑的短期状态就是工作记忆。

**经验记忆**回答的是"系统学到了什么"。它保存任务执行过程中的成功路径、失败教训和抽象出来的策略模式。比如你纠正过它一次写法，告诉它"这种代码不能这么写"，它就把这次教训沉淀下来，下次遇到类似场景主动绕开。这让智能体具备在复杂环境中自我迭代的能力，也是目前比较前沿的方向。

### 记忆形态

#### Token 级记忆

- 显式、离散，容易编辑；存储形式一般是对话记录或文本块，在向量数据库中存一条 JSON 或结构化文本即可，增删改都比较方便，透明可追溯。
- 适合多轮对话机器人、个性化推荐系统，或金融、医疗、法律这类强安全约束的场景。
- Token 级记忆是当前的主流。

##### Token 级记忆的演进

> 1D 平坦结构 → 2D 平面结构 → 3D 分层结构

- **1D 平坦结构**：全量的简单对话列表、经验池或切分块；实现简单，但检索粒度粗——比如存了一年的聊天记录，想从中定位某条信息会非常困难。
- **2D 平面结构**：知识图谱、树状结构或关系表，通过节点和边显式建立对象 / 实体之间的联系；检索时可以沿着点边游走，在长跳推理上表现很好。
- **3D 分层结构**：多层摘要 / 图 / 金字塔结构，底层是全量稀疏数据，上层是少量稠密数据，支持垂直导航。

#### 参数化记忆

- 将知识固化在模型参数中，可以通过监督微调、LoRA 或强化学习等方法改变模型参数。
- 比如经典做法是用优质数据集对模型进行强化或微调。
- 隐式、抽象，通常有更高的性能上限，不需要走"检索再推理"这条路；缺点是更新慢，而且存在严重的灾难性遗忘——学会新技能的同时会覆盖掉旧的参数。
- 适合场景比如角色扮演——把特定角色的性格、语气和价值观喂进去，之后每次都遵循这套规则，而不必在提示词里反复提醒；或者推理密集型任务，又或者需要掌握根本性强、能力强的任务，比如让模型学会一种全新的复杂代码框架，把"这种框架该怎么写"强化到它的参数里。

#### 潜空间记忆

- 机器原生，存储隐藏状态、激活值，或高度压缩的 KV、中间层输出，不需要经过后续 decoder 层输出；通常更紧凑、节省 token，因为不必像 Token 级记忆那样作为 prompt 塞进上下文窗口，也方便多模态融合。
- 缺点是解释性和可编辑性弱。
- 适合场景比如多模态记忆，或端侧、边缘部署等需要高压缩比的场景。

### 记忆的形成、演进和调用

从功能讲完，再看记忆在智能体内部是如何形成、演进、被调用的。整套循环可以划分为三个阶段，加上贯穿其中的更新与遗忘机制——这套**形成 → 演进 → 检索**的动态闭环，正是现代智能体记忆系统与传统数据库最根本的差异。

**形成阶段**做的是从原始的、海量的交互数据里提炼真正高价值的信息。智能体不可能把每句废话都存下来，必须借助大模型在语义层做摘要、知识蒸馏，或者通过参数化把经验直接注入模型本体。形成阶段如果不克制，记忆库很快就会被噪声污染。

**演进阶段**处理的是新旧记忆的冲突与衰减。新提取的记忆要融进现有记忆库，同时解决逻辑冲突——昨天用户还说"我喜欢 Go"，今天又说"我现在用 Rust"，老记忆需要被新的覆盖；过时、错误的内容也要被主动淘汰。如果缺乏有效的演进机制，长期运行的智能体迟早会被冗余信息拖垮，推理成本飙升而检索精度下降。

**检索阶段**不只是"查一查"。智能体需要判断什么时候才该去翻记忆，在用户表述不清时还要做查询重写——"我喜欢他"，"他"到底指谁？召回出来的多个碎片也要重新排序，把最相关的放在前面。

贯穿这三个阶段的是**遗忘策略**。常见的有三种思路：基于时间衰减模拟人脑的遗忘曲线，越久远、越低频的记忆权重越低；基于频率借鉴 LRU 调度，频繁被使用的记忆留在核心区，长期不用的下沉到边缘；基于价值与语义则是大模型时代特有的解法——直接让 LLM 充当裁判，对每条记忆做主观打分，把低分内容清洗掉。没有行之有效的遗忘策略，长程运行的智能体就会被噪声拖垮，这也是 memory 系统跟"更大的数据库"最关键的区别。

## Mem0：Token 级记忆的工程化样本

Mem0 是 GitHub 上 Token 级记忆里使用最广的开源实现，代码很值得一读——可以非常直观地看清一个完整的记忆 pipeline 是怎么搭出来的。这里挑三件事来看：**记忆怎么写入（add）、怎么检索（search）、底层是怎么存的**。

### Add：先整理再落库

Mem0 的添加并不是"收到一句聊天就直接塞进数据库"，而是先用大模型把原始对话整理成**独立无歧义的事实句**，再做持久化。这一步依赖三种输入一起喂给 LLM：最近 10 条原始上下文（用来补全指代——"他"是谁、"那个"是什么），通过语义相似度召回的 10 条最相关旧记忆（用来理解用户的长期语境），加上当前这条新消息。LLM 在这三者基础上压缩出一条可以独立看懂的事实句，并顺手做一次语义层去重——如果发现已经有等价的旧记忆，就不再重复写入。

事实句生成之后才进入系统层落库。Mem0 会先用 embedding 生成向量，再做一次词形还原（把"I am eating"还原成"eat"，去掉时态、复数、标点等冗余），后者专门服务于后续 BM25 关键词匹配。然后把向量、原文、关键词文本、创建/更新时间一并写入向量库。

写库之后还有一步**实体绑定**——从规范句中抽出人名、物品名等实体，存进单独的实体库，并和对应的记忆 ID 关联起来。这个机制是 Mem0 最近一次重要重构的产物，后面会专门讲。

整个 add 流程的核心是三道收缩：作用域收缩（按 user / agent / run 隔离命名空间，避免跨用户串数据）、语义去重（让 LLM 在生成事实句时主动规避重复）、哈希去重（避免完全相同的文本被多次写库）。三层叠在一起，记忆库才不至于随时间膨胀失控。

### Search：三路并行召回 + 可选重排

收到 query 后，Mem0 会先对它做三种预处理：向量化、关键词化（给 BM25 用）和实体抽取。然后并行触发三路召回——**向量余弦相似度（主召回）、BM25 关键词匹配、实体增强**——分别打分后做加权融合，得到每条记忆的总分。如果开启了 rerank，结果再交给一个大模型做一次重排序。

向量召回拿"语义相近、用词不同"的记忆，BM25 拿到精确的关键词（比如查 `bug-1234` 这种代码），实体增强则负责"和这个实体相关的所有记忆"加分。三路融合比单纯的向量召回鲁棒得多。

### Update / Delete 与底层存储

Mem0 在数据层维护三个库：向量库存所有的记忆向量及原文，SQLite 存添加、更新、删除历史以及原始上下文，实体库存实体本身以及实体到记忆 ID 的映射。

Mem0 最近做了两次比较激进的变更，都很值得关注。

**第一个变更：从读写混合改为 append-only。** 之前调用 add 时，底层可能会触发 add / update / delete 三种操作——Mem0 会让 LLM 在写入时判断是否有旧记忆需要更新或删除。这套机制慢、耗 token，而且 LLM 容易把重要历史误删。新版本改成了纯追加模式：任何新信息都像写日记一样直接追加，并附带最新时间戳，写入延迟直接砍掉一半。原本由 update/delete 解决的旧记忆失效问题，全部交给检索阶段——通过时间戳过滤或 LLM 重排，让最新、最相关的记忆胜出。

**第二个变更：砍掉知识图谱，改用实体绑定。** Mem0 之前也走双重召回，其中一路是知识图谱遍历——每次 add 都要先抽事实、再抽实体和关系、组装三元组，然后同时写入向量库和图数据库。这套链路慢、易错、延迟高，且在大部分场景下并未带来明显的效果提升。所以 Mem0 直接废弃图数据库，把专有名词作为标签挂在向量上，检索时通过实体关联做底层加分。一次 LLM 调用、一次数据库写入，延迟再次减半。

这两次变更体现了一个共同的工程直觉：**LLM 在写路径上的复杂决策（要不要更新、要不要删除）很容易拖垮系统**，把这类判断后置到检索侧、用时间戳和重排来兜底，往往更稳。把图谱完全替换成"实体标签 + 向量加分"也提醒我们，在 99% 的场景里，知识图谱并不是性价比最高的选择——除非业务确实强依赖多跳关系推理。

## MemGen：让"回忆"和"推理"同步发生

最后看一篇 ICLR 2026 的论文——MemGen。它直接挑战了上面两条记忆路线（参数化、Token 级）的局限：参数化记忆改的是 backbone 权重，会带来灾难性遗忘；Token 级记忆通常是"先检索、后推理"的一次性调用，缺少在生成过程中"灵光一现"的能力。

人在解题时其实并不是这样的——我们读着读着题，突然想到"诶，这一步可以这么做"，这是一种**和推理同步发生的回忆**。MemGen 想要的就是这种能力。

### 三模块设计

MemGen 把整个系统拆成三块。**冻结的推理器**就是主大模型，全程不动，从根上避免了参数化记忆的灾难性遗忘问题。**Trigger** 是一个轻量 LoRA，监控推理器中间层的隐藏状态，判断"我现在是不是需要回忆一下"。**Waver** 是另一个轻量 LoRA，一旦被 Trigger 召唤，它会基于当前 hidden state 生成一段固定长度的 **latent token** 序列，直接拼回推理器的隐藏状态序列里，作为后续生成的依据。

整个机制有点像人类解题时突然冒出的直觉——Waver 输出的不是自然语言提示，而是机器原生的高维向量，直接和模型当前的内部状态对齐，省掉了"先把直觉翻译成自然语言、再被模型重新编码"这一步。

### 几个聪明的设计点

Trigger 没有在每个 token 都做前向计算，而是只在**句子分隔符处（逗号、句号等）**触发激活检查——这些位置往往对应逻辑转折点，正则匹配即可定位，几乎没有额外开销。训练时通过强化学习引入"调用频率惩罚项"，让 Trigger 学会只在真正需要外部经验时才暂停推理。

Waver 的训练完全独立于推理器主体，只更新自己的 LoRA 权重，所以不会影响主模型的常识能力。它学到的更多是**策略型、规划型**的高阶知识——"遇到分类讨论怎么拆解"、"代码生成时怎么对齐合规检查"——而不是事实性记忆。

举个具体例子：在解 |2x − 3| = 5 时，模型先正常生成"首先我们要去掉绝对值符号，需要……"。在这个逗号处，Trigger 检测到中间层隐藏状态的不确定性飙升（因为要进入分类讨论的逻辑分叉），于是暂停生成，把控制权交给 Waver；Waver 根据当前 hidden state 生成一段表示"分类讨论"策略的潜在向量，拼回隐藏状态序列，模型继续往下推理。

### 三个维度的创新

可以把 MemGen 的创新概括为三条：**时间维度**上，从"先检索再推理"变成"边推理边回忆"，回忆嵌入到生成过程中而不是任务起点；**空间维度**上，摒弃自然语言 prompt，直接在潜空间传递高密度认知特征，省 token；**架构维度**上，用 Trigger + Waver 两个轻量 LoRA 把"何时回忆"和"回忆什么"解耦。

### 实验中的几个意外

论文在 9 个跨领域基准上做了验证，几个比较有意思的结果：

**跨领域泛化非常强。** 在数学领域训练好的 Waver 模块，零样本平移到其他领域时准确率不降反升——因为它沉淀下来的是"遇到多步复杂任务时如何拆解目标"这类抽象策略，而不是具体公式。面对完全陌生的领域，Trigger 会自动降低触发频率，避免胡乱调用不成熟的记忆。

**持续学习中没有遗忘。** 传统微调会改主模型权重，导致旧任务掉点；MemGen 由于主模型冻结，旧任务准确率几乎不动。

**推理延迟反而下降。** 这是最反直觉的——本来频繁暂停应该拖慢端到端速度，但实验里整体推理时间不增反减。原因是：基线模型遇到难题时会胡乱试错、吐出大量无效 token；MemGen 注入的几枚 latent token 帮模型更快锁定正确路径，省下来的远多于暂停带来的开销。

**Waver 内部自发分化出层次。** 在没有任何人工指令的前提下，Waver 学到的潜空间居然自发分化成**规划型、程序型、工作型**三种记忆——这和前面综述里讲的智能体记忆三分法不谋而合。

### 几点思考

MemGen 和外部知识库检索并不冲突，可以协同——它本质上更像一个"认知编译器"，解决的是"过程中需不需要灵光一现"，而 RAG 解决的是"事实从哪里来"。

另外，用 LoRA 去固化记忆这条思路本身很有吸引力：推理性能高、不污染主模型权重，特别适合**长期、稳定、不需要频繁更新的策略型记忆或用户画像**。甚至可以训练多个 LoRA，配一个路由器根据当前任务类型动态选择走哪一份"记忆"——这是论文之外一个值得继续展开的方向。不过这里也有一个尚未解决的问题：当用户的偏好或事实型记忆需要持续更新时，静态 LoRA 显然不太够用，MemGen 自己也没在这条路上给出答案。

机制上，MemGen 把"latent token 拼到 hidden state 后面"和**投机解码**有几分异曲同工：投机解码也是先用某种廉价手段生成一串候选 token，再交给主模型继续往下推理。从这个角度看，MemGen 像是把投机解码里的"草稿生成器"换成了"经验回忆器"。
