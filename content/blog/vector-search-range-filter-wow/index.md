带范围过滤的 ANN（range filter ANN）是这两年 SIGMOD/VLDB 的一个高频赛道:查询同时带一个向量和一个标量区间 `[l, r]`,要在区间内的向量里找最近邻。商品价格区间、按时间窗口找最相似图片,都属于这一类。SIGMOD'26 R2 的 WoW 是这一方向上比较新、思路也比较干净的一篇。把它放在 IRangeGraph、DIGRA、SERF、HSIG 这条线上看,它在动态插入这条支线上的取舍变得很直观。

## 背景:范围过滤为什么不能直接套图索引

最朴素的两个方案,从字面上就能想出来:

- **Pre-filtering**:先按属性把区间内的向量过滤出来,再在子集上暴力算距离。选择度极高(过滤后只剩万分之几)时,这是最优解——根本没有索引能比"过滤后纯暴力"更快,因为索引本身的导航开销已经超过了直接算 distance。
- **Post-filtering**:先用 Ann 索引找一批 top-k',再筛掉不在区间内的。这条路只在选择度低(大部分点都在区间内)时有效;如果区间只命中 1%,你 top-1000 都未必凑得齐 10 个合法点。

把这两个思路搬到图索引上,问题马上暴露:

- **Pre-filtering on graph**:搜到一个点之后,只往合法邻居走,非法邻居整段忽略。问题是当合法点很少时,图的连通性塌掉,搜两步就停了,召回率断崖下跌。
- **Post-filtering on graph**:非法邻居也参与导航(只是不进结果集)。代价是路径会变得非常长,大量计算花在不在区间内的点上。

所以这条赛道上发出来的论文,几乎都在做一件事:**用一种数据结构去管理"按属性切分的多份图"**,让查询时只动相关的那部分图,把过滤这步固化到索引结构里。

## 路线一:线段树 + 图(IRangeGraph)

IRangeGraph 是这条路上最早把思路说清楚的一篇,SIGMOD'25。思路对打过算法竞赛的人来说毫无门槛:把属性离散化成 1 到 n,在 `[1, n]` 上建一棵线段树,每个节点对应一段区间;每个节点都建一张图。

查询 `[l, r]` 时,线段树把这个区间拆成 O(log n) 个节点,只搜这些节点的图,然后合并结果。线段树本身完成了"过滤"这步,图上做的就是普通 Ann。

**动态选边**是这篇文章一个有意思的工程细节。查询时不是真的把所有节点的图一张张搜过,而是在线段树上做自顶向下的探索:当前在某个点 v,先看根节点图里 v 的邻居,在 `[l, r]` 内的拿出来;不够 m 条边就往下一层看,直到凑够。覆盖关系冗余的层(`[1,8]` 和 `[5,8]` 在 `[6,15]` 内重合)直接 skip。

代价也很直接:图建多了。n=1e8 大概要建 30 多张 HNSW,索引大小是原始向量的 4-5 倍。而且是纯静态索引——线段树本身就不支持插入。

实测在 selectivity 极高(2^-10 这种)的场景,IRangeGraph 比 pre-filtering 没优势,因为这种 corner case 暴力扫描就是最优。但在中等选择度上,它是当时的 SOTA 之一。

## 路线二:B+ 树 + 图(DIGRA)

DIGRA 是线段树思路的一个 incremental work。线段树不支持插入,那就换 B+ 树。

结构基本同构:B+ 树的每个内部节点对应一段属性范围,每段建一张图。建图时把子图直接合并到右子图里(用 HNSW 的探针搜索插入),省下来一部分代价。

新的优化点在查询:DIGRA 不严格匹配 query range,而是允许用一个"近似 range"去逼近实际 range。论文给了个定理:用两个 B+ 树节点的图覆盖任意 query range,最坏情况近似 range 不会超过实际 range 的 4 倍。本质是放宽过滤的精度换取扫描的图节点数。

插入的代价就比线段树小很多了——只需要 split/merge 的部分子图,而不是从头重建。但它的插入仍然有非常重的开销:每次 split 都需要重新建那一段的图,标记删除。对真正大规模的流式插入场景仍然不够好。

## 路线三:全压缩到一张图(SERF / DSG)

SERF 走的是一条很极端的路:对每一种可能的 `[l, r]`,理论上都要建一张图;但作者发现可以**把所有这些图无损压缩到一张图上**。

核心观察:在按属性排序后的点序列上,固定左界 `l=1`,只看右界 `r` 从 1 增长到 n 的过程,每条边都有一个"生存期":它在某个 r 点诞生(被加入邻居),在某个更大的 r' 点被 RNG 裁掉。也就是说每条边都对应一个连续区间 `[b, e]`,只有当查询的 r 落在这个区间内,这条边才是活跃的。

把这个观察推广到任意 `[l, r]`(2D Segment Graph),每条边变成一个五元组 `[(l_range), (r_range), neighbor_id]`。查询时只走"边的生存期覆盖了 query range"的边。

效果是索引大小直接降到一个 HNSW 量级,远小于 IRangeGraph/DIGRA 那种 log n 倍。代价是只能按属性顺序静态构建——一旦数据来了新点,整个排序基础就乱了,需要重排重建。

DSG(Dynamic Segment Graph)是 SERF 的后续工作,试图把这套压缩扩展到流式无序插入。思路是:对每个新点,证明在它的可能查询范围被切成若干小矩形之后,每个小矩形内的 KNN 是唯一确定的——然后只对这些唯一 KNN 建带生存期的边。

但 DSG 的实测结果索引大小依然非常大,边数远超 SERF,在动态场景下的查询性能也没有 SERF 在静态场景的那种代差优势。

## 路线四:统一前/后/混合过滤(HSIG / UNIFY)

VLDB'25 的 UNIFY(论文里叫 HSIG)走的是另一种思路:把 pre/post/hybrid 三种策略集成在一张图上。

核心是 Hybrid 索引:按属性深度直方图把数据分成 s 个段,每段点数大致相同;每个点除了在自己段内连 KNN,还在其他每个段里都连一组 KNN。这样查询 `[l, r]` 时,在一张图上走,每跳只看那几个相关段的邻居链表就行。

辅助结构:每个点的邻居链表分 s 组(每个段一组),配一个跳表支持 pre-filtering,配一个 bitmap 标注原始 HNSW 边支持 post-filtering。两个阈值 τ_a/τ_b 决定 query range 落在哪个区间用哪种策略。

HSIG 的真正卖点是支持流式插入——它的整套结构都是 incremental 的,新点插入只动当前段附近。代价是空间开销大约是原始数据集的 3 倍,在 query range 很小(2^-10 这种 corner case)的时候,性能依然比不过 IRangeGraph 这种为该场景特化的。

## WoW 的核心:层次化窗口图

铺垫了这么久,终于到 WoW 本身。它的出发点其实最朴素:

如果我们提前知道 query range 是 `[l, r]`,那只对这个范围内的合法点单独建一张图,这张图就是当前查询下最理想的邻近图——论文管这叫 **Oracle Graph**。每一步搜索都走在合法点上,没有任何浪费。

现实当然不可能每个 query 都建一张图。所有 range filter ANN 本质上都是在用一张通用的图去逼近 Oracle Graph。WoW 的逼近策略是:**对每个点都在一组属性窗口内连边**。

具体来说,给定一个窗口大小 w,点 i 只能在 `|rank(j) - rank(i)| ≤ w/2` 的点里选邻居。窗口里的邻居本身就在属性上接近,所以这种边非常符合"Oracle Graph 下应该存在"的结构。

但单一窗口大小不够用。Oracle Graph 里 `(15, 14)` 可能是一条边,但在 w=4 的窗口图里这条边不存在(因为 16 比 14 离 15 更近,会抢占边的位置)。要让 `(15, 14)` 重新出现,15 那个点得有一个 w=2 的更小窗口图。

于是 WoW 把不同窗口大小的图叠成多层。层号 L,窗口大小 `2·O^L`,O 是扩张系数。论文里推导出 O=4 是最优值。

```
L=2: 大窗口 (w=32)    →  覆盖全局,粗导航
L=1: 中窗口 (w=8)     →  中等选择度的过滤
L=0: 小窗口 (w=2)     →  高选择度,几乎都是合法邻居
```

每一层都包含全量节点(只是连的边不一样),不像 HNSW 上层稀疏下层密集。

## WoW 的搜索:跨层动态选边

WoW 的搜索逻辑跟 HNSW 看似相似,实质不同。HNSW 上层只为快速定位,只在最底层做多领域搜索。WoW 每一层都是一张完整的 NSW,搜索时**每一跳同时翻多个层级的邻居表**。

这么设计的理由是:固定大小的窗口图各有所长。高层图跳得远但噪声大(非法点多);低层图边少但都合规。让每一跳同时利用高层的导航能力和低层的"干净邻居",避免陷入局部最优。

搜索算法在每一跳检查邻居的合法性,有一套早停策略:**一旦发现某一层的邻居全部合规,就不再往更低层翻**。理由是这一层已经能提供高质量合法导航,继续往下搜更短的边纯属浪费。

查询的起点也不是固定的最高层。WoW 用 WBT(weight balanced tree)在 O(log n) 时间内估算 query range 内的合法点数 N',然后挑一个窗口尺度最接近 N' 的层作为**着陆层**,从那一层往下搜。这一层在结构上就是当前 query 最接近 Oracle Graph 的层。

## WoW 的插入:无序流式,局部修补

WoW 的真正卖点是无序增量插入。新点 v 来的时候:

1. **算窗口**:用 WBT 在 O(log n) 时间内算出 v 在每一层的窗口范围。这里 WBT 只是个轻量插件,跟图本身完全解耦——不像 RangePQ 那种把树和向量索引紧耦合的方案。
2. **找候选邻居**:从最高层往下,每层做一次 beam search 找 M 个候选;关键是**复用上一层的结果**——上层窗口大,如果筛选后落在当前层窗口内的候选已经够多,就不再做完整搜索,直接复用。论文里证明了一个定理:高层窗口的邻居距离平均比低层更近,且若它符合低层窗口范围,它一定也存在于低层中。
3. **建边 + 两阶段剪枝**:
   - 不一次性把 M 个候选都连上,只连 M/2 条边,留余量给后续插入。
   - 邻居表满了触发剪枝:第一阶段是**窗口检查**(新点加入后邻居窗口边界变了,把已经明显出窗口的旧邻居删掉);第二阶段是 RNG 剪枝(删冗余边)。
4. **延迟剪枝**:不立即删掉那些"刚刚因为新点插入而失去合法性"的旧边。因为 WoW 是动态图,后续可能再有新点插入,窗口又会变化,过早删边会破坏图的导航稳定性。只在邻居表真的满了、需要让位给更好的邻居时才真正剪掉。

这套策略的本质是:**所有维护操作都是局部的**。新点插入只影响 WBT 窗口附近的连接,不需要像线段树/B+ 树那种全局重构。这也是 WoW 能在持续无序插入下维持图质量的核心原因。

插入时间复杂度的最坏情况是 O(log²n),比 HNSW 略高;但实测因为大量复用,实际开销并不比 HNSW 高多少。16 线程并行扩展能到 5-6.9x。

## 实验中的几个关键数据点

WoW 这篇文章实验工作量相当大,把前面提到的所有 baseline 都跑了一遍。几个值得注意的点:

- **总体性能**:在混合负载下,WoW 在 90% recall 处比 IRangeGraph 快约 1.4 倍,比 HSIG 快约 4 倍。一个支持动态插入的索引能达到静态索引的性能水平,是很强的信号。
- **图质量**(用 DC,距离计算次数衡量):WoW 几乎和 Oracle Graph 重合,在 95% 高 recall 区间也没有产生太多冗余计算。这是两阶段剪枝 + 延迟淘汰策略的直接效果。
- **早停 + 着陆层**:消融实验里,加了早停之后 QPS 显著上升、DC 显著下降。每一跳的探索层级从无早停的 4-5 层降到 1-2 层。
- **极端 selectivity**:在 2^-10 这种 corner case,IRangeGraph 因为每跳都要做 O(log n) 的线段树遍历,开销大;SERF 因为有损压缩容易丢合法邻居;WoW 因为着陆层选得准,性能更稳。
- **困难数据集**(GIST、Wikidata4M):向量分布稠密,图质量决定一切,WoW 和 IRangeGraph 这种依赖高质量图的方案明显优于其他。SIFT 这种稀疏分布上各方案差距就不大。
- **索引大小**:WoW 大约是 HNSW 的 2-3 倍。原因很清楚——每一层都是全量点,边数会多。但比 IRangeGraph 那种 log n 张图的方案小不少。在高维数据上(GIST 960维),这个膨胀比例其实非常温和,因为点本身只存一份,膨胀只来自边的存储。

## 几个判断

读下来的几个个人感受:

**1. WoW 是这条赛道里第一篇把"无序流式插入 + 全选择度 + 接近 Oracle 图质量"三个目标同时做到的方案。** IRangeGraph 静态、DIGRA 插入代价大、SERF 静态且范围受限、HSIG 在 corner case 上性能差——它们都各自缺了一块。WoW 的窗口图 + WBT + 两阶段剪枝 + 延迟淘汰组合起来才把这件事做成。

**2. 它的"新"主要在系统性的设计组合,而非单一算法。** 窗口图概念在 NSG/HNSW 之前就有,WBT 是经典数据结构,RNG 剪枝是图索引标配。把这些组件按"局部性优先"的原则拼起来,得到了一个支持完全增量动态更新的结构,这种工程层面的整合是论文真正的贡献。

**3. 这套结构特别适合 agent memory 场景。** 智能体的记忆随对话不断生成,需要随时增量插入;检索时经常按时间窗口过滤。WoW 的窗口机制和 WBT 索引在这种场景下比传统层级结构(LNG 那种)更顺手。但要注意 agent memory 的查询模型常常是"反过来"的——查询带一个时间戳,库里向量带时间范围——这种"双时态"查询目前还没有现成方案,需要额外工程改造。

**4. 它的几个明显未解问题。**
- 只支持单属性过滤,多个范围属性同时过滤要重新设计。
- 内存占用相对较大(每层全量点),把底层窗口图换到磁盘/SSD 上是个自然的扩展方向。
- WoW 的边按层组织,放到 disk 上时"一个点的边怎么存"会变成新问题:全连续存会让普通 Ann 查询带很多无用 IO(读上来的 block 里有大量无关层的边);按层切分又会触发跨 block 读。这部分目前没人系统做过。
- GPU 上做 range filter ANN 的工作几乎没有(label filter 的 GPU 工作也只有 WebFlow 一篇,效果一般)。WoW 的多层结构天然适合并行,把它搬到 GPU 上可能是一个值得做的方向。

**5. 真正的统一索引还远没解决。** WoW 至少能很好地兼容"无过滤"的普通 Ann 查询(走最上层就行),但 label filter 这边的 LNG/UNG 这条路连这都做不到——它们各个子图之间连通性太差,纯 ANN 性能直接崩。同时支持任意条件(range + label + 正则)且共用一套索引,目前还是开放问题。
